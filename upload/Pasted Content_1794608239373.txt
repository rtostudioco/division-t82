# 2. IDENTIDAD DEL PRODUCTO

Nombre de trabajo: DIVISION T82

Descripción:

Cross-Platform Security Engineering & Posture Assessment Platform.

Objetivo:

Desarrollar una aplicación de escritorio capaz de evaluar y explicar la postura de seguridad de:

- Windows 11.
- Windows 10 cuando sea compatible.
- Linux Ubuntu LTS.
- Linux Debian estable.
- macOS en arquitecturas Apple Silicon e Intel, sujeto a compatibilidad técnica y pruebas.

No afirmes que una plataforma es compatible hasta que sus comprobaciones funcionales hayan sido probadas.

La aplicación debe permitir que un usuario principiante o intermedio comprenda la seguridad de su propio equipo sin necesitar conocimientos avanzados de ciberseguridad.

El producto debe ser útil tanto para aprendizaje individual como para auditorías técnicas locales y pequeñas infraestructuras empresariales.

## Filosofía del producto

1. Local-first.
2. Privacy-first.
3. Security-by-design.
4. Read-only by default.
5. Modular architecture.
6. Explainable findings.
7. Evidence-based assessment.
8. Cross-platform adapters.
9. Human-controlled remediation.
10. Extensible through documented APIs.

No debe convertirse en un antivirus, EDR, SIEM, herramienta de explotación o plataforma de pentesting indiscriminado.

Su especialización es Security Engineering.

# 6. UNIVERSAL SECURITY ENGINE

Este será el núcleo del producto.

El motor debe separar:

A. Reglas comunes.
B. Reglas específicas por plataforma.
C. Adaptadores de recopilación.
D. Normalización de evidencias.
E. Evaluación de resultados.
F. Puntuación explicable.
G. Informes.

## Contrato de reglas

Cada control debe tener:

- ID único.
- Nombre.
- Descripción.
- Categoría.
- Severidad.
- Plataforma aplicable.
- Versiones o distribuciones compatibles.
- Condición que evalúa.
- Fuente de evidencia.
- Estado del resultado.
- Explicación técnica.
- Referencias documentales.
- Recomendación de corrección.
- Método de verificación.

Las reglas deben estar versionadas y validadas mediante un esquema estricto.

No permitas que un archivo YAML o JSON descargado pueda ejecutar código arbitrario.

## Estados obligatorios

Conserva los estados existentes cuando corresponda:

- PASS
- FAIL
- WARNING
- NOT_APPLICABLE
- NOT_ASSESSED
- ERROR

Una comprobación sin permisos suficientes debe ser NOT_ASSESSED o ERROR, nunca PASS.

Una función que no existe en un sistema operativo no debe ser evaluada como un fallo.

Separa el nivel de cobertura del nivel de seguridad.

No inventes un score de 100 cuando una parte importante del sistema no pudo evaluarse.

## Security Evidence Schema

Define un contrato común versionado para normalizar los resultados.

Debe permitir registrar:

- Record ID.
- Host ID.
- Sistema operativo.
- Versión del sistema.
- Distribución.
- Control ID.
- Estado.
- Severidad.
- Evidencia.
- Método de recopilación.
- Fecha UTC.
- Nivel de confianza.
- Privilegios requeridos.
- Referencia documental.
- Limitaciones.
- Recomendación.

Cada hallazgo debe conservar trazabilidad hacia su evidencia original.

# 7. ADAPTADORES NATIVOS POR SISTEMA OPERATIVO

Los adaptadores deben compartir una interfaz común, pero utilizar fuentes de datos adecuadas para cada plataforma.

Windows 11 y Windows 10 compatible.

- Usuarios y grupos locales.
- Privilegios.
- UAC.
- Windows Defender.
- Windows Defender Firewall.
- Estado de BitLocker.
- TPM.
- Secure Boot.
- Servicios activos.
- Procesos.
- Puertos y conexiones.
- Actualizaciones.
- Configuración de seguridad.
- Aplicaciones instaladas.
- Políticas locales cuando sea posible.

Fuentes técnicas candidatas:

- Windows Management Instrumentation.
- CIM.
- APIs documentadas de Windows.
- Registro de Windows, en lectura.
- Cmdlets documentados de PowerShell.
- Interfaces nativas autorizadas.

Ejemplos de comprobaciones de referencia:

- Get-MpComputerStatus
- Get-NetFirewallProfile
- Estado de BitLocker.
- Estado de UAC.
- Estado del arranque seguro.

No dependas exclusivamente de comandos PowerShell si existe una API nativa más apropiada.

No modifiques configuraciones durante una auditoría.

## 7.2 LINUX ADAPTER

Prioridad inicial:

- Ubuntu LTS.
- Debian estable.

Diseña el adaptador para facilitar la incorporación futura de Fedora y distribuciones adicionales.

Áreas:

- Usuarios y grupos.
- sudo y privilegios.
- Configuración de SSH.
- Firewall.
- UFW.
- nftables.
- Servicios systemd.
- Procesos.
- Puertos abiertos.
- Paquetes instalados.
- Estado de actualizaciones.
- AppArmor.
- SELinux, cuando corresponda.
- Cifrado LUKS.
- Permisos de archivos sensibles.
- Configuración de red.

Fuentes de datos:

- /etc/
- /proc/
- /sys/
- systemd.
- journalctl.
- Gestor de paquetes.
- APIs o herramientas nativas documentadas.

No asumas que todas las distribuciones tienen las mismas herramientas, rutas, servicios o políticas.

Detecta la distribución y la versión antes de aplicar reglas específicas.

## 7.3 macOS ADAPTER

Objetivo:

macOS compatible con arquitecturas Apple Silicon e Intel, una vez validadas.

Áreas:

- FileVault.
- Gatekeeper.
- System Integrity Protection.
- Firewall.
- Usuarios administradores.
- Actualizaciones.
- Servicios launchd.
- Aplicaciones instaladas.
- Configuración de red.
- Permisos relevantes.
- Estado de protecciones del sistema.

Utiliza herramientas y APIs oficiales de Apple.

Respeta TCC, SIP y las restricciones de privacidad del sistema.

No intentes evadir permisos.

La integración con Endpoint Security debe considerarse una fase avanzada e independiente, con los requisitos de autorización, entitlements y distribución documentados.

## Regla esencial

Una misma función puede tener diferentes métodos de recopilación en cada sistema.

El resultado final debe seguir el contrato común, no obligar a las plataformas a comportarse de manera idéntica.

5. Configuración actual.
6. Configuración recomendada.
7. Comandos o pasos manuales.
8. Archivos afectados.
9. Posibles efectos secundarios.
10. Requisitos previos.
11. Procedimiento de rollback.
12. Método para verificar la corrección.

No modificar firewall, SSH, permisos, usuarios, servicios, registro, políticas, cifrado ni actualizaciones.

La ejecución futura, si se desarrolla, deberá ser un componente separado, explícitamente autorizado y con controles adicionales.

# 9. SEGURIDAD INTERNA DE LA APLICACIÓN

Esta aplicación maneja información sensible del sistema operativo. Su propia seguridad debe ser prioritaria.

Implementa:

- Principio de mínimo privilegio.
- Modo de lectura por defecto.
- Separación entre frontend y colectores.
- Validación de entradas.
- Protección ante command injection.
- Protección ante path traversal.
- Protección ante SSRF en conectores.
- Control de acceso a archivos.
- Límites de recursos.
- Protección de secretos.
- Logs estructurados.
- Redacción de información sensible.
- Dependencias verificadas.
- Actualizaciones seguras.
- Trazabilidad de operaciones.

Reglas estrictas:

1. No utilizar shell=True.
2. No ejecutar comandos proporcionados por el usuario.
3. No ejecutar instrucciones obtenidas de un modelo de IA.
4. No ejecutar código recuperado de documentos.
5. Usar listas cerradas de comandos y argumentos permitidos.
6. Definir timeouts y límites de salida.
7. No requerir administrador/root para iniciar.
8. Solicitar elevación solo cuando sea imprescindible.
9. No evadir restricciones del sistema operativo.
10. No enviar telemetría automáticamente a servidores externos.

Si una comprobación requiere permisos especiales, explicar al usuario qué dato no pudo obtenerse y por qué.

Preparar un threat model de la propia aplicación.

# 16. INSTRUCCIONES DE TRABAJO PARA TI

Quiero un proceso de ingeniería real.

No generes todo el código de golpe.

Primero inspecciona el proyecto y crea un diagnóstico.

Después produce la arquitectura definitiva y el roadmap técnico.

A continuación implementa las fases en orden, conservando lo que funciona.

En cada fase debes:

1. Explicar el objetivo.
2. Identificar los archivos que se modificarán.
3. Diseñar antes de implementar.
4. Implementar el código funcional.
5. Ejecutar pruebas.
6. Corregir errores.
7. Ejecutar build.
8. Documentar resultados.
9. Mostrar las funciones terminadas.
10. Identificar pendientes y riesgos.

No uses placeholders que simulen funcionalidades terminadas.

No dejes botones sin acción.

No inventes métricas.

No afirmes que un adaptador está listo si solo devuelve datos de prueba.

No ocultes errores con valores predeterminados.

No destruyas funcionalidades actuales para simplificar el desarrollo.

Si una decisión tecnológica presenta problemas, explica la alternativa, sus consecuencias y la razón del cambio.

Si falta una dependencia o capacidad del entorno, documenta el bloqueo y continúa con el trabajo que sí pueda realizarse.

Toma decisiones técnicas razonables sin pedir confirmación por cada detalle menor.

Cuando existan riesgos de pérdida de datos, cambios de permisos, privilegios o modificación del sistema operativo, detente antes de ejecutar la acción.
